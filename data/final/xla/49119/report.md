# [XLA:GPU] `IndexingMap` composition through `dynamic-update-slice` binds runtime variables to the wrong start operands

- Repository: `openxla/xla`
- Report: [https://github.com/openxla/xla/issues/49119](https://github.com/openxla/xla/issues/49119)
- Opened: 2026-09-19T21:34:02Z
- Closed: open at collection time
- Labels: `bug`, `stat:awaiting openxla-eng`, `NVIDIA-GPU`, `GPU`

## Reported behavior

## Summary

A loop fusion containing a reverse cumsum, a pad/crop, a `dynamic-update-slice` with three traced start indices, and a traced `roll` (concatenate + dynamic-slice) produces wrong results on XLA:GPU (CPU JIT and op-by-op execution seem to be correct). The output-to-operand `IndexingMap` that the GPU emitters compute for the DUS *update* operand has its runtime variables rotated: the roll's start is substituted where the DUS start of dimension 0 belongs, and the three DUS starts are shifted by one slot. The base-operand map of the same fusion is correct.

## Reproducer (GPU shows the bug, CPU is the ref. )

```python
import os
os.environ.setdefault("XLA_PYTHON_CLIENT_PREALLOCATE", "false")
import numpy as np, jax, jax.numpy as jnp
from jax import lax

def f(x, start0, start1, start2, shift):
    t = jnp.flip(jnp.cumsum(jnp.flip(x, 2), axis=2, dtype=jnp.int32), 2)     # reverse cumsum
    t = lax.pad(t, jnp.int32(0), [(-3, -1, 0), (1, 2, 0), (-2, -3, 0)])        # crop/pad -> (29, 10, 11)
    update = lax.dynamic_slice(t, [0, 0, 0], (14, 4, 7)) * 3 - 1
    t = lax.dynamic_update_slice(t, update, [start0, start1, start2])          # (20,5,1) clamps to (15,5,1)
    return jnp.roll(t, shift, axis=1)                                          # traced shift

def reference(x):
    t = np.flip(np.cumsum(np.flip(x, 2), axis=2, dtype=np.int64).astype(np.int32), 2)
    t = np.pad(t[3:32, :, 2:13], ((0, 0), (1, 2), (0, 0)))
    update = t[:14, :4, :7] * np.int32(3) - np.int32(1)
    result = t.copy(); result[15:29, 5:9, 1:8] = update
    return np.roll(result, 5, axis=1)

shape = (33, 7, 16)
x = (np.arange(np.prod(shape), dtype=np.int64).reshape(shape) * 7919 % 10007 - 5000).astype(np.int32)
expected = reference(x)
args = (jnp.asarray(x), jnp.int32(20), jnp.int32(5), jnp.int32(1), jnp.int32(5))
for platform in ("gpu", "cpu"):
    with jax.default_device(jax.devices(platform)[0]):
        got = np.asarray(jax.jit(f)(*args))
        with jax.disable_jit():
            eager = np.asarray(f(*args))
    bad = np.argwhere(got != expected)
    print(f"{platform}: jit={'OK' if not bad.size else 'WRONG'} op-by-op={'OK' if np.array_equal(eager, expected) else 'WRONG'} "
          f"bad={bad.shape[0]} first={bad[0].tolist() if bad.size else None}")
```

Output:

```
gpu: jit=WRONG op-by-op=OK bad=748 first=[0, 6, 2]
cpu: jit=OK op-by-op=OK bad=0 first=None
```

## Environment

- jax 0.11.2 / jaxlib 0.11.2 (PyPI, 2026-09-17) with the CUDA 13 plugin; also jax 0.12.0.dev20260919 nightly.
- XLA `645c721` (2026-09-19) for the dumps and `print_indexing` output above.
- RTX PRO 4000 (compute capability 12.0), driver 595; CPU control on the same host.

## Trigger

A fused computation combines three dynamic-update-slice starts with a later runtime dynamic-slice start generated by roll.

## Relevant entities

composed IndexingMap; first-map runtime variables; second-map runtime variables; DUS start operands; dynamic-slice start operands; update tensor coordinates

## Implemented relation

Each runtime symbol in a composed affine indexing expression is bound to the start operand whose domain and position the expression assumes.

## Pre-state

The two component maps each carry ordered runtime variables for their own dynamic start operands.

## Binding transition

ComposeIndexingMaps places second-map runtime symbols before first-map symbols, while ComposeOperandIndexing and ComposeInstructionIndexing append the backing variable records in the opposite order.

## Post-state

The composed expression's rt0, rt1, and later symbols read different start operands than their declared domains describe.

## Validity obligation

The ordered runtime-variable record list matches the symbol order produced by affine-map composition.

## Invalid decision

The indexing analysis concatenated first.runtime_variables before second.runtime_variables although the composed map uses second before first.

## Physical effect

The update indexing map substitutes the roll start where the first DUS start belongs and shifts the remaining DUS starts.

## Observed consequence

The fused GPU program returns 748 incorrect elements in the report, while CPU JIT and op-by-op execution match the reference.

## Repair site

xla/hlo/analysis/indexing_analysis.cc::ComposeOperandIndexing and xla/codegen/tiling/symbolic_tile_analysis.cc::ComposeInstructionIndexing

## Repair

Commit e298fb6 reorders both runtime-variable lists to second-then-first, updates expected symbolic tiles, and adds a DUS-plus-dynamic-slice indexing regression and GPU correctness coverage.

## Why the repair works

Runtime values and affine symbols now use the same composition order, so each clamped start operand controls its intended tensor dimension and operation.

## Causal basis

The maintainer identifies this commit as the indexing-map repair; its message names the reversed runtime-variable ordering, and its regression composes dynamic-update-slice with dynamic-slice exactly as the report does.

## Analysis implication

Indexing analysis needs affine symbol order, runtime-variable identity, variable domain, source instruction, composition direction, and the final physical coordinate expression together.

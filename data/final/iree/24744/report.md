# [Codegen][LLVMCPU] Un-hoisted in-loop stack alloca in the matmul overflows the worker stack

- Repository: `iree-org/iree`
- Report: [https://github.com/iree-org/iree/issues/24744](https://github.com/iree-org/iree/issues/24744)
- Opened: 2026-07-22T14:42:10Z
- Closed: 2026-07-24T06:40:35Z
- Labels: `bug 🐞`, `regression`

## Reported behavior

Compiling a plain `linalg.matmul` with `--iree-opt-data-tiling=true` **and** `--iree-llvmcpu-disable-distribution=true` produces a matmul dispatch whose inner tile loop contains a `memref.alloca` that is **not hoisted out of the loop and never freed inside it**. The stack pointer is decremented every iteration with no restore, so the worker-thread stack grows unboundedly and overflows (`EXC_BAD_ACCESS`) once the tile count is large enough. Small matmuls run fine; large ones crash.

## Repro

`matmul_8192.mlir`:
```mlir
func.func @matmul(%A: tensor<8192x8192xf32>, %B: tensor<8192x8192xf32>, %C: tensor<8192x8192xf32>) -> tensor<8192x8192xf32> {
  %0 = linalg.matmul ins(%A, %B : tensor<8192x8192xf32>, tensor<8192x8192xf32>)
                     outs(%C : tensor<8192x8192xf32>) -> tensor<8192x8192xf32>
  return %0 : tensor<8192x8192xf32>
}
```

```bash
iree-compile matmul_8192.mlir \
  --iree-hal-target-backends=llvm-cpu \
  --iree-llvmcpu-target-cpu=apple-m4 \
  --iree-opt-data-tiling=true \
  --iree-llvmcpu-disable-distribution=true \
  -o matmul_8192.vmfb

iree-run-module --module=matmul_8192.vmfb --function=matmul \
  --input=8192x8192xf32 --input=8192x8192xf32 --input=8192x8192xf32
```

Expected:
```
EXEC @matmul
[1]    40218 bus error  iree-run-module --module=matmul_8192.vmfb
```

## This is a regression folks :D

The leaking in-loop `alloca` is generated by a **recent compiler** but not by an older release:

| compiler | date  | runs |
|---|---|:---:|
| release `3.11.0rc20260316` @ `e4a3b0405d` | 2026-03-16 | OK |
| `main` @ `4b11e1da59b1` | 2026-07-16 | **crash** |

## Trigger

A large data-tiled matmul is compiled with distribution disabled, leaving loadProcessorData in the inner loop.

## Relevant entities

worker-thread stack; loop iteration; processor-data alloca; feature-bit stores; microkernel call

## Implemented relation

A temporary processor-data slot has function lifetime and consumes one bounded stack allocation, while per-call feature updates remain adjacent to the microkernel call.

## Pre-state

The worker thread enters the tile loop with a fixed stack budget.

## Binding transition

loadProcessorData emits memref.alloca/LLVM alloca at the loop-local builder insertion point on every iteration.

## Post-state

Each iteration decrements the stack pointer without restoring it until function return.

## Validity obligation

Function-lifetime scratch storage is allocated once outside loops, and loop-local code performs only bounded updates.

## Invalid decision

DispatchABI constructed the processor-data allocation at the caller's current insertion point without separating storage reservation from per-call feature patching.

## Physical effect

Stack consumption grows linearly with the matmul tile count.

## Observed consequence

Large matmuls overflow the worker stack and crash, while small matrices complete.

## Repair site

compiler/src/iree/compiler/Codegen/LLVMCPU/DispatchABI.cpp::HALDispatchABI::loadProcessorData

## Repair

PR 24749 moves construction to the function entry block. PR 24786 refines the change: only the alloca is hoisted, while feature-bit stores remain at the call site so inlined microkernel checks still devirtualize. Both include IR checks for loop placement.

## Why the repair works

The stack slot is allocated once per invocation, so loop count no longer changes stack usage, while call-local stores preserve optimization behavior.

## Causal basis

The report identifies the loop-local alloca; both linked merged patches name #24744, and the refinement explicitly separates the stack-allocation cause from feature-bit stores needed for devirtualization.

## Analysis implication

A stack-lifetime check needs allocation insertion block, enclosing loops, iteration count, stack budget, escape/lifetime boundary, and per-call operations that cannot be hoisted.

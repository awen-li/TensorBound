# torch.compile miscompilation when copying from and saving to a state tensor in the same fused kernel

- Repository: `pytorch/pytorch`
- Report: [https://github.com/pytorch/pytorch/issues/164701](https://github.com/pytorch/pytorch/issues/164701)
- Opened: 2025-10-05T18:45:38Z
- Closed: 2025-10-07T18:17:51Z
- Labels: `high priority`, `triage review`, `triaged`, `module: correctness (silent)`, `oncall: pt2`, `module: inductor`

## Reported behavior

### 🐛 Describe the bug

In the below notebook cell, there are three versions of a function that rotates new rows into a state tensor whose purpose is to contain the last 2048 rows. `slide_to_the_left1` is just included for reference; it should have the same behaviour as the other two functions. `slide_to_the_left3` is just a `torch.compiled` copy of `slide_to_the_left2`: however it does not behave the same as `slide_to_the_left2` and instead exhibits a miscompilation bug.

These functions are a minimal-ish version of a much larger codebase that was both updating the state tensor and then using it to perform some computation (hence the seemingly useless `dev_null` tensor in the reproducer); it's not from a fuzzer.

The script is set up to initialise a state tensor with zeros, slide two new events into the state tensor, and then check that only the last two rows of the state tensor are nonzero; for them to be nonzero would be a bug. It does not crash/print an error, this is a bug report of a miscompilation.

```python
import os

os.environ["TORCH_LOGS"] = "output_code"

import torch
import torch.nn

device = "cuda"

def slide_to_the_left1(state, new_events, arange, dev_null):
    _ = arange
    _ = dev_null

    concatenated = torch.cat([state, new_events], dim=1)
    state[:, :, :] = concatenated[:, -2048:, :]

def slide_to_the_left2(state, new_events, arange, dev_null):
    batch_size, _, _ = new_events.shape

    concatenated = torch.cat([state, new_events], dim=1)

    # these three lines are a very complicated identity transformation:
    batch_idx = torch.arange(batch_size, dtype=torch.int32, device=device)[:, None]
    arange = arange[None, :]
    concatenated = concatenated[batch_idx, arange]

    state[:, :, :] = concatenated[:, -2048:, :]
    dev_null[:, :, :] = concatenated[:, :, :]

slide_to_the_left3 = torch.compile(slide_to_the_left2)

state = torch.zeros([4, 2048, 1024], device=device)
slide_to_the_left1(
    state,
    torch.arange(start=1, end=3, device=device)[None, :, None].expand(4, 2, 1024).contiguous(),
    torch.arange(2050, dtype=torch.int32, device=device),
    torch.zeros([4, 2050, 1024], device=device),
)
display("slide_to_the_left1", state)
# because new_events has shape [4, 2, 1024], only 2 new events should have been added to the state, and the rest should still be zeros:
assert (state[:, :-2, :] == 0).all(), torch.nonzero(state[:, :-2, :])

state = torch.zeros([4, 2048, 1024], device=device)
slide_to_the_left2(
    state,
    torch.arange(start=1, end=3, device=device)[None, :, None].expand(4, 2, 1024).contiguous(),
    torch.arange(2050, dtype=torch.int32, device=device),
    torch.zeros([4, 2050, 1024], device=device),
)
display("slide_to_the_left2", state)
# ditto
assert (state[:, :-2, :] == 0).all(), torch.nonzero(state[:, :-2, :])

# this third one has a race condition that can take a few attempts to be exhibited on a T4
# anecdotally it seems to happen more often on the bigger chips
# single digit attempts to exhibit this have always sufficed on the NVIDIA chips I've tried
for attempt in range(1, 1000):
    state = torch.zeros([4, 2048, 1024], device=device)
    slide_to_the_left3(
        state,
        torch.arange(start=1, end=3, device=device)[None, :, None].expand(4, 2, 1024).contiguous(),
        torch.arange(2050, dtype=torch.int32, device=device),
        torch.zeros([4, 2050, 1024], device=device),
    )

    if not (state[:, :-2, :] == 0).all():
        display(f"slide_to_the_left3 attempt {attempt}", state, torch.nonzero(state[:, :-2, :]))
        break
```

If we look at the triton generated by torch.compile here, you can see that it generates a kernel for the `state[:, :, :] = concatenated[:, -2048:, :]` copy step that simultaneously reads from `in_ptr1` and `out_ptr1`, and then it invokes that kernel passing `arg1_1` for both `in_ptr1` and `out_ptr1`. This creates a race condition whereby sometimes a block can be read after a different part of the GPU has already written the rotated values (i.e., those slided 2 to the left), and so you can see in this example where we start with zeros and the two new rows are to be added to slot 2046 and 2047, parts of those new rows can also get duplicated into slot 2044 and 2045; in general this can cause much more shuffling of the state.

## Trigger

A compiled state update concatenates the old state with new rows, reads a shifted slice of that logical result, and copies the slice back into the original state tensor while another output also consumes the concatenation.

## Relevant entities

state tensor storage; concatenation and indexed slice; scheduler WeakDep; read index map; write index map; fused Triton kernel; temporary materialization

## Implemented relation

A read from mutable storage remains ordered before a later write to that storage when their index maps differ; the ordering edge survives every fusion round unless the fused operation is pointwise in place at matching indices.

## Pre-state

The state read supplies the old rows needed to construct the shifted result, and the copy back to state is ordered after those reads.

## Binding transition

During repeated fusion, the scheduler removed the WeakDep after observing another dependency on the fused upstream node without checking whether the read and write index maps were compatible for in-place fusion.

## Post-state

The generated Triton kernel received the same state allocation as both an input and output and read shifted locations while other program instances wrote the destination range.

## Validity obligation

A write-after-read dependency is removed only when every relevant read and the mutation access the same buffer positions with compatible iteration domains.

## Invalid decision

_prune_redundant_deps treated the presence of another upstream dependency as sufficient to discard the mutation-ordering edge.

## Physical effect

Parallel Triton program instances could overwrite state elements before other instances completed the shifted reads from those elements.

## Observed consequence

The compiled function intermittently copied newly inserted rows into earlier state positions, while eager execution retained zeros outside the final two rows.

## Repair site

torch/_inductor/scheduler.py::_prune_redundant_deps, Scheduler.fuse_nodes_once, and Scheduler.fusable_weak_dep

## Repair

Commit f34744d checks fusable_weak_dep before pruning a WeakDep, performs dependency pruning before each fusion round, rejects broad StarDep writes, and validates all relevant reads against the mutation's index and size. It adds an in-place flip regression whose read and write indices differ.

## Why the repair works

The scheduler keeps the ordering edge for shifted or otherwise nonmatching reads, preventing those reads from sharing a kernel with the mutation. The fixed #164701 output materializes the shifted result into a temporary buffer and copies that buffer into state in a later kernel.

## Causal basis

The report identifies a fused kernel that receives the state tensor as both input and output and performs shifted reads concurrently with writes. Commit f34744d landed before the report, states that WeakDeps prevent fusion of reads and writes with different indexing, and adds a matching in-place shifted-read regression. A PyTorch maintainer asks the reporter to test post-2.8 nightly because of a recently fixed dependency problem, runs the full reproducer successfully, shows the new temporary-buffer boundary in generated code, and attributes the result to the author of PR 162316.

## Analysis implication

Fusion analysis needs storage identity, read and write index functions, iteration sizes, mutation order, dependency-pruning decisions, and the final kernel argument aliases together.

# iree-compile generates empty function for fmaf (RISCV32)

- Repository: `iree-org/iree`

- Closed: 2023-07-24T20:43:48Z
- Labels: `bug 🐞`, `codegen/riscv`

## Reported behavior

### What happened?

@hcindyl and myself are running a small model that consists of a single softmax layer (1x2xi8), on an rv32im core. At execution time, we noticed that the output doesn't match what's expected. I traced through the execution, and at some point, there's a call to `fmodf` that ends up returning NaN, and then math collapses :)

In the intermediate assembly generated by iree-compile, I do not see any call sites for `fmodf`, but do see many calls to `fmaf` -- and this is also reflected in the dumped IR: `fma` is what we expect, not `fmod`.

In the intermediate assembly, there exists a function definition for `fmaf` with no body, followed by a definition of `fmodf` with a body:

```
	.section	.text.fmaf,"ax",@progbits
	.p2align	2
	.type	fmaf,@function
fmaf:
.Lfunc_begin23:
	.cfi_startproc
.Lfunc_end23:
	.size	fmaf, .Lfunc_end23-fmaf
	.cfi_endproc

	.section	.text.fmodf,"ax",@progbits
	.p2align	2
	.type	fmodf,@function
fmodf:
.Lfunc_begin24:
	.cfi_startproc
	addi	sp, sp, -16
	.cfi_def_cfa_offset 16
	sw	ra, 12(sp)
	sw	s0, 8(sp)
```

It seems like this empty `fmaf` method probably shouldn't exist, and a call out to libm woud be appropriate instead? Any idea what causes this empty method to be generated?

`iree-compile --mlir-print-ir-after-all -iree-llvmcpu-target-triple=riscv32-pc-linux-elf -iree-llvmcpu-target-cpu=generic-rv32 -iree-llvmcpu-target-cpu-features="+m" -iree-llvmcpu-target-abi=ilp32 person_detection_c_module_static.mlir --iree-llvmcpu-keep-linker-artifacts --iree-hal-target-backends=llvm-cpu --iree-llvmcpu-link-static --iree-llvmcpu-link-embedded=false --iree-hal-dump-executable-intermediates-to=/tmp/iree -o /dev/null`

## Trigger

A static RISC-V build sets --iree-llvmcpu-link-embedded=false and contains floating-point fused multiply-add calls.

## Relevant entities

LLVM module; fmaf symbol; embedded musl bitcode; external libm; linkEmbedded option

## Implemented relation

Each runtime math call resolves to the implementation selected by the executable's embedded-library policy.

## Pre-state

The build disables embedded builtins and expects unresolved math symbols to be supplied by the final system link.

## Binding transition

The old target linker unconditionally links IREE's musl bitcode even when linkEmbedded is false.

## Post-state

An imported fmaf declaration from the embedded module becomes an empty definition in the generated object and intercepts the expected external call.

## Validity obligation

Embedded builtin modules participate in IR linking only when the embedded-link option is enabled.

## Invalid decision

LLVMCPUTarget linked the musl module independently of the user's linkEmbedded setting.

## Physical effect

Calls bind to an empty fmaf body and execution falls into invalid floating-point behavior.

## Observed consequence

The softmax produces incorrect output after the math path returns NaN on RV32.

## Repair site

compiler/src/iree/compiler/Dialect/HAL/Target/LLVMCPU/LLVMCPUTarget.cpp

## Repair

PR 14246 places musl bitcode linking under options_.linkEmbedded, leaving those symbols for the external static link when the option is false.

## Why the repair works

The generated object now follows one consistent symbol-provider policy instead of mixing disabled embedded linking with embedded declarations.

## Causal basis

The report isolates an empty fmaf definition under link-embedded=false, and the merged patch gates the exact unconditional musl link on that option.

## Analysis implication

Executable-link analysis needs the symbol, provider module, import/definition state, target ABI, and embedded-link option.
